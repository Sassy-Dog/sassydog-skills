# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A **Claude Code plugin marketplace** containing a single plugin (`sassy-dog`) that bundles reusable skills and review agents for Claude Code, Gemini CLI, and other AI coding tools. Repo visibility is `INTERNAL` (the Sassy Dog org default).

There is **no build step** — the entire repo is Markdown (skills/agents) plus the Bash scripts bundled inside skills' `scripts/` directories. CI (`.github/workflows/ci.yml`, required on `main`) runs `bash scripts/preflight.sh` — the single source of truth for every gate: shellcheck (`-S warning`), `scripts/check-frontmatter.sh` (two layers — **loader** requirements on every tracked skill/agent file: frontmatter `---` on line 1, `name`/`description` present, name matches directory/filename; plus the **Agent Skills spec** constraints on `SKILL.md` only: `description` ≤ 1024 characters, `name` ≤ 64 characters with charset and hyphen rules, and a strict frontmatter key allowlist whose unknown keys hard-fail, so CI cannot go green on a file `gh skill publish` would refuse — `agents/*.md` are exempt from the spec layer because an agent legitimately carries `color:`), the positional-token and legacy-name guards, manifest JSON validation + the CalVer version-of-record guard, the versioning tests (`scripts/test-versioning.sh`), the ownership-matcher tests (`scripts/test-ownership-matchers.sh` — the `setup-hooks`/`setup-deps` `generated-by:` matchers, extracted from the shipped `SKILL.md` and run against real pre-rename consumer artifacts committed verbatim under `scripts/fixtures/legacy-markers/`), the label-taxonomy tests (`scripts/test-label-taxonomy.sh` — the cross-set CIEDE2000 colour check via `align-labels.sh --collisions`, `issue-claim.sh`'s label reconcile exercised against a mock `gh`, and the no-third-copy guard that searches every colour from both `taxonomy` emitters across the tracked tree and fails on any hit outside its own home; definitions and a mock only, never a live repo), the label-migrate tests (`scripts/test-label-migrate.sh` — `align-labels.sh --migrate`'s relabel-then-delete gate against a mock `gh` that records writes, plus the source-level single-call-site invariant and a mutation that neuters the gate; the mode itself is **never** run in CI, because it deletes labels in other repos), the dependabot-render tests (`scripts/test-dependabot-render.sh` — `setup-deps` renders one lane per (ecosystem, **directory**) and every lane is backed by a manifest in the directory it names, against three recorded consumer layouts under `scripts/fixtures/dependabot-render/`, with the collapsed-to-`"/"` pre-#169 shape required to FAIL validation; recorded file lists only, no repo and no network), and markdownlint (`.markdownlint-cli2.jsonc`) — plus a separate dockerized actionlint step. **Run `bash scripts/preflight.sh` locally before every PR** (`--fix` auto-fixes markdownlint findings). Those gates are necessary but not sufficient: "correctness" still means accurate trigger phrases and skill instructions that actually work when invoked — verify changes by installing the plugin locally (below) and exercising the skill.

## Layout (flat — everything at root)

This repo *is* the plugin; there is no nesting under a plugin subdirectory.

```
.claude-plugin/
  plugin.json        # plugin manifest — version is the version-of-record, stamped by scripts/stamp-version.sh (never hand-edit)
  marketplace.json   # marketplace entry pointing at the GitHub repo
agents/
  *-reviewer.md      # subagents, auto-discovered, namespaced sassy-dog:<name>
skills/
  <skill>/
    SKILL.md         # required: frontmatter (name + description) + instructions
    references/      # optional: deep reference docs (progressive disclosure)
    scripts/         # optional: executable tools the skill calls
```

## How the pieces fit together

Two non-obvious architectures live in this repo.

### Generator + capability skills (the dev-workflow family)

- **The six workflow skills are generic and ship in the plugin.** `survey-work` (prioritized work plate), `groom-backlog` (backlog grooming), `take-it` (parallel issue-shipping, "take #341, #432"), `dispatch-ready` (loop dispatcher), `send-it` (single-PR end-to-end), and `tidy-repo` (post-shipping git reconciliation) each have exactly ONE implementation, under `skills/`. Per-repo behavior lives in that repo's `.claude/sassy-dog/<skill>.md` config, read at load time via dynamic context injection. The format is `setup-config/references/config-contract.md`. **There is no per-repo copy of these skills** — that is what makes every invocation render namespaced (`sassy-dog:survey-work`) and what removes the trigger-phrase competition an earlier generated-skills design had to design around.
- **`NO_CONFIG` is a first-class state.** A skill invoked in a repo with no config must derive what it safely can and run in its most conservative mode. Two exceptions block instead, because both act unattended and outward-facing: `take-it` (dispatches sub-agents) and `dispatch-ready` (dispatches and merges on a loop).
- **Configure only what cannot be derived.** Repo slug, default branch, and `delete_branch_on_merge` come from `gh repo view` at runtime; they never appear in config. A configured value is a value that can drift.
- **Workflow skills are thin and delegate.** Shared mechanics live in the capability skills — `github-issues` (board/issue reads, dedupe-then-file writes), `sentry-triage` (gate-and-escalate), `pr-shepherd` (polling, merge queue vs direct, coupled-PR serialization, worktree teardown), `repo-cleanup` (the `tidy-repo` engine: `[gone]`/squash branch sweep, stash triage, untracked sweep — reuses `pr-shepherd`'s `teardown.sh --sweep`), `repo-health` (TODO/CI/lag scans), `testflight`. They invoke them by namespaced name (`sassy-dog:<skill>`); fix mechanics in the capability skill, never in a workflow skill. **`repo-cleanup` keeps its name** — it is now a capability-boundary distinction (mechanics vs. the user-facing flow) rather than the trigger-collision avoidance it was originally named for.
- **Consumer repos must declare BOTH the marketplace and the plugin in their own `.claude/settings.json`.** Two keys, and both are load-bearing in cloud sessions: `extraKnownMarketplaces` declares where the `sassydog-skills` marketplace lives (`{"sassydog-skills": {"source": {"source": "github", "repo": "Sassy-Dog/sassydog-skills"}}}`), and `enabledPlugins` selects the plugin from it (`"sassy-dog@sassydog-skills": true`). `enabledPlugins` alone is **not** sufficient: it references the marketplace only by name, and marketplace registration otherwise lives in user-level state (`~/.claude/plugins/known_marketplaces.json`), which never transfers to a cloud VM — so every local session works (the user registered the marketplace once) while a cloud session or scheduled routine cannot resolve `@sassydog-skills` and silently loads no skill (issue #97: the daily fire-watch routine fired and produced nothing). Cloud sessions install repo-declared plugins at session start *from the marketplace the repo declares* (docs: Settings → `extraKnownMarketplaces`; Cloud environments → "What carries over"); this requires network access to the marketplace source. This repo declares itself; see `.claude/settings.json`.
- **Routine prompts carry a skill-load fallback as contract, and its degraded-load signal is a REQUIRED FIELD, never a discretionary sentence.** Because plugin install at cloud-session start can still fail (network, auth to an INTERNAL repo), every scheduled-routine prompt that invokes a plugin skill must include a fallback clause so a loading gap degrades loudly instead of silently no-op'ing. **A "note the degraded load" sentence alone is insufficient — it is discretionary, and it has already been dropped**: on 2026-08-11 the weekly run hit `Unknown skill: sassy-dog:whats-behind` in its own log and delivered a complete, authoritative-looking report with no note at all, while the run 24h earlier carrying the identical clause did include one (#146, and it poisoned #144's evidence). A missing sentence reads as "fine"; an empty slot in a structured header reads as broken. So both report skills carry an always-rendered `Load:` field on their header line (`plugin` or `fallback (degraded)`), and the routine clause names it. Exact clause for the daily fire-watch routine: "If `sassy-dog:whats-on-fire` is not among your available skills, read `skills/whats-on-fire/SKILL.md` from the repo checkout and follow it exactly, noting the degraded load in your output and rendering `Load: fallback (degraded)` in the report header." Exact clause for the weekly routine: "If `sassy-dog:whats-behind` is not among your available skills, read `skills/whats-behind/SKILL.md` from the repo checkout and follow it exactly, noting the degraded load in your output and rendering `Load: fallback (degraded)` in the report header." Use the same shape (skill name + its `skills/<name>/SKILL.md` path + the `Load:` field) for any new routine. **The field is still the run reporting on itself, so it is never the authority: where the report and the run log disagree, the run log wins.** The out-of-band check that settles it — the `Unknown skill: sassy-dog:<name>` signature, where it appears in a run log, and how to read its absence — is [`docs/ROUTINES.md`](docs/ROUTINES.md); consult the log, not the report, whenever load state is being used as evidence.
- **`setup-config` is a config generator, not a runtime skill.** Run inside a product repo it writes `.claude/sassy-dog/*.md` plus the `.claude/settings.json` plugin declaration. It renders no skill bodies. Its modes: **migrate** (a repo still on generated skills — extract config from them, verify, then delete), **update** (config already present), **adopt** (legacy hand-written skills), **create** (nothing yet). Siblings `setup-hooks` and `setup-deps` follow the same generator pattern for hooks and Dependabot config.
- **`setup-repo` is the umbrella orchestrator over those three, and carries no generation logic.** It owns only the broad "set up this repo" intent — the three generators keep their own specific vocabularies, and a description that swallowed them would make the specific invocations ambiguous. It picks which generators apply, prints one combined plan of every file they would touch, gets approval, then runs them **strictly in sequence** (`setup-config` → `setup-hooks` → `setup-deps`) and reports what ran, what was skipped, and why — a skipped generator is a reported outcome, never a silent no-op. **The order is load-bearing.** `setup-config` and `setup-hooks` both write `.claude/settings.json` — the marketplace/plugin declaration and the `hooks.PostToolUse` entry — and both merge surgically into their own keys rather than rewriting the file, so sequential runs compose while a concurrent or last-write-wins run drops one of the two *silently* (both contracts are report-and-skip, not error; a prior migration lost a consumer's `PreToolUse` push guard to exactly this class of overwrite). Never dispatch the generators as parallel sub-agents. Mechanics stay in the generators: fix detection, mode selection, or ownership matching there, never in the orchestrator.
- **One delegation mode.** Independent/vendored mode was removed — it was the only path that could produce an unbranded, un-namespaced skill, and no repo used it. Everything delegates `Skill: sassy-dog:<cap>`; `pr-shepherd` remains the script root (`repo-cleanup` ships no scripts and calls its `teardown.sh`; `github-issues` calls its `gh-retry.sh`).
- **`setup-hooks` is the same generator pattern one layer down**: it detects a consumer repo's stack (keyed on repo config presence, never installed binaries) and renders a single PostToolUse formatter/linter dispatcher into `.claude/hooks/sassydog-post-edit.sh` + a `.claude/settings.json` entry. It has **two ownership markers, and they behave differently under a rename**: the *settings entry* is owned by command path (`.claude/hooks/sassydog-`), which no producer rename touches; the *script* is owned by its `generated-by:` producer name, which is committed inside every consumer repo. So the script matcher must accept every producer name this generator has emitted (`setup-hooks`, `refresh-hooks`, `refresh-sassydog-hooks`) across both marker namespaces (`sassy-dog:` and `ai-agent-skills:`), emit the current name on write, and normalise — a matcher narrowed to the current name would classify every pre-rename consumer script as hand-written and skip it *silently*, since the contract is report-and-skip, not error. Re-runs reconcile only owned entries and never touch hand-written hooks. The template (`references/templates/sassydog-post-edit.template.sh`) is valid shellcheck-clean bash with ALL tool blocks present — rendering only deletes `# {{IF:TOOL}}` blocks, so every render is valid by construction. Like the config generator, it always runs from the plugin.
- **The two generators' render invariants are deliberately DIFFERENT, and neither should be restated as the other's.** `setup-hooks` stays **deletion-only** (above): one hook script per repo, no per-location repetition, so every render is valid by construction. `setup-deps` is **validated after render** (issue #169): a Dependabot lane is a (ecosystem, **directory**) pair and a monorepo needs the same ecosystem at several directories — velovate npm at four, tailoredtip bun at two — which deletion cannot express, so `dependabot.yml.template` v3 repeats a block per location and `scripts/validate-dependabot.sh` parses the render and asserts every emitted `directory:` actually holds the manifest it claims. That trade is strictly stronger *here*: the static guarantee never caught the bug, because a v2 render was always valid YAML that pointed at directories with no manifests, and Dependabot answers that by silently doing nothing. Two consequences worth keeping: `render-dependabot.sh` **refuses to default a lane to `/`** when a location cannot be derived (it drops the block and says so), and `validate-dependabot.sh --compare-to` catches the **diverged-but-owned** file — marker says "mine", content is past what a fresh render reproduces — and fails instead of overwriting, which is the state tailoredtip was in when this was found.
- **Config format: frontmatter is regenerated, `##` prose is carried across verbatim.** That split is the whole point — prose is what a refresh must never rewrite. Contract: `setup-config/references/config-contract.md`; migration: `references/migrate-mode.md`. **Marker recognition must accept every producer name** (`refresh-skills`, `refresh-sassydog-skills`, legacy `create-dev-workflows`) **and both marker namespaces** (the current `generated-by: sassy-dog:` prefix and the pre-rename `generated-by: ai-agent-skills:` prefix) — an unrecognised marker drops the repo into create mode and silently loses its config. That producer list is frozen history for the superseded `.claude/skills/<name>/SKILL.md` path; `setup-config` is deliberately **not** on it, because the `.claude/sassy-dog/*.md` config it writes carries no `generated-by:` marker at all.
- **Write paths are concentrated.** `github-issues/scripts/file-or-link-issue.sh` is the single issue-creation path (marker-keyed idempotency, `--dry-run`, preview-then-confirm, burst rail). `sentry-triage` never mutates Sentry. Keep it that way.

### Orchestrator + reviewer agents (`assess-it`)

The relationship between the `assess-it` skill and the nine `*-reviewer` agents requires reading `skills/assess-it/SKILL.md` + `orchestration.md` together:

- **`assess-it` is an orchestrator.** It runs a 5-phase audit: detect stack → fan out reviewer agents concurrently (one message, multiple Agent calls) → adversarially verify each finding → cluster into PR-sized work → preview and file GitHub Issues under a tracking Epic.
- **The `*-reviewer` agents are the fan-out workers.** Each owns a domain (architecture, code-quality, security, testing, cicd-release, infra-platform, observability-ops, dx-docs, dependency-supply-chain) and runs in **audit mode**: it FINDS problems and cites `file:line` evidence, it does NOT write code. The agent→domain dispatch map lives in `orchestration.md`.
- **All agents return the same finding schema** (title, area, severity, likelihood, evidence, why_it_matters, proposed_fix, acceptance, pr_size, labels, confidence). When editing one reviewer's output contract, keep it consistent with the schema in `orchestration.md` and the other agents.
- `github-secrets` and `testflight` are standalone capability skills — no agent orchestration.

## Conventions that matter

- **Skill `description` is a trigger spec, not a summary.** It is dense with quoted user phrases ("set a GitHub secret", "check TestFlight feedback") because matching those phrases is what activates the skill. When adding/editing a skill, write the description as the list of utterances that should trigger it.
- **Progressive disclosure.** SKILL.md stays thin and actionable; depth goes in `references/*.md` that the skill says to read "when you reach that phase." Don't inline reference-doc detail into SKILL.md.
- **Reviewer agents carry a "Sassy Dog calibration" section** applied only when the relevant stack is present (e.g. Doppler is the secrets source of truth, all-secrets/zero-`vars.*`, managed identity + Key Vault `kv-sassydog`, pin Actions to SHAs). New org-wide policies belong in the matching reviewer's calibration block.
- **No bare `$1`–`$9`/`$@`/`$*` in SKILL.md bodies or dev-workflow templates.** Skill bodies are arg-substitution surfaces: when a skill is invoked with args (as every thin generated skill invokes its capability skill), positional tokens in the rendered body get replaced with args tokens, corrupting embedded commands. CI greps for them (`skills/*/SKILL.md`, `.claude/skills/*/SKILL.md`, `setup-config/references/templates/*`). The guard now asserts that template pathspec is non-empty first — an empty pathspec used to make it pass while covering nothing. Use `cut -f1`/`%(format)` idioms instead, or move the snippet to a `references/` doc or bundled script — neither is substituted.
- **Outward-facing actions require preview-then-confirm.** `assess-it` never files GitHub Issues silently — it prints the full Epic + child-issue preview and files only on approval. Preserve this guard in any change.
- **Irreversible actions are gated structurally, not by ordering.** `scripts/align-labels.sh --migrate` folds a repo's one-off labels onto the canonical set, and deleting a label strips it from every issue carrying it unrecoverably. "Relabel first, delete second" is therefore control flow, not a comment: `gh label delete` has exactly ONE call site, inside `migrate_delete_gate()`, whose own body re-queries GitHub immediately above it and returns without deleting on every path that is not "zero issues still carry the old label" — including "the re-query itself failed", because unknown is not verified. The relabel loop's counters are not a parameter of that function; the migration's own success message is never the evidence. `scripts/test-label-migrate.sh` asserts the single-call-site invariant against the script's source and mutation-proves the gate. Any new destructive capability goes behind the same shape: one call site, its own fresh verification in the same body.
- **A taxonomy consumer runs the owner or reads its `taxonomy` emitter — it never transcribes the table.** Two tables exist: `scripts/align-labels.sh` (10 engineering dimensions + 4 severities) and `skills/github-issues/scripts/issue-claim.sh` (the 4 dev-workflow state labels). Each exposes `taxonomy` (`name|color|description`; no gh, jq, repo or network), and each reads the other through it — that is how `--collisions` scores both sets without a copy. `assess-it` was the counter-example: a third transcription in a reference doc, frozen at the pre-#158 colours, so #158 recolouring `tech-debt` created an `infra`/`tech-debt` collision *inside a file #158 never saw*, shipped into every repo it audited — and its `gh label create … || true` could not have corrected one anyway (issue #167). It now invokes `align-labels.sh --repo <target>`; gate 8 fails on any taxonomy colour found outside its home. Note **`${CLAUDE_PLUGIN_ROOT}` is substituted into `SKILL.md` at load time only** — not into `references/*.md` (read raw) and not into the shell environment — so a plugin script path that a reference doc needs must be resolved in `SKILL.md` and passed in.
- Conventional commits (`feat:`, `fix:`, `chore:`, `docs:`). Recent history uses PRs to `main`.

## Local development

```bash
# Run Claude Code with this plugin loaded from the working tree
claude --plugin-dir ~/Repos/sassy-dog/sassydog-skills

# Install from the published marketplace
claude plugin marketplace add Sassy-Dog/sassydog-skills
claude plugin install sassy-dog
```

After editing a skill or agent, reload via `--plugin-dir` and invoke the skill to confirm frontmatter parses and triggers fire.

## Releasing

The plugin version is **monthly-rolling CalVer** (`YYYY.M.<commits-this-month>`, e.g. `2026.7.16`) per the org Versioning spec; the committed `version` in `.claude-plugin/plugin.json` is the version-of-record. **Never hand-edit it** — stamp it:

```bash
bash scripts/stamp-version.sh   # resolves CalVer and writes .claude-plugin/plugin.json
```

Commit the stamped manifest in the release PR. Build number: N/A for this repo; tags optional. Full instance doc — including the **one-way ratchet** (no `0.x`/`1.x` may ever follow CalVer): [`docs/VERSIONING.md`](docs/VERSIONING.md). Keep `README.md`'s plugin/skill table and the agent list in sync when skills or reviewer agents are added or removed.
